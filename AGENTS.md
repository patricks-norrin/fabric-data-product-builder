# Toolpack Maintenance Instructions

This repository builds and maintains the packaged `nor-data-product-builder` agent and its `nor-*` skills.
These instructions govern work **in this repository only**. They do not replace the behavior of the packaged agent
in `agents/nor-data-product-builder.agent.md`, and they do not govern customer data-product projects generated by it.

## External Test Loop

The user tests the packaged agent in a separate session on a fresh WSL2 Ubuntu image with GitHub Copilot CLI. They
install the latest toolpack version with:

```text
/plugin install norrin-fabric-data-product-toolpack@norrin-fabric-plugins
```

The user runs the packaged agent there, then brings this builder agent the observed output, failures, and improvement
requests. Treat that feedback as the primary acceptance signal. Improve the smallest owning agent, skill, script, or
notebook template here; preserve unrelated behavior.

## Implementation Rules

- Before changing data-product behavior, read the relevant vendored `reference/lakehouse_toolbelt/docs/` pages and
  `reference/lakehouse_toolbelt/examples/` samples. They define the pattern to implement, not a starting point for a
  replacement design.
- Prefer KISS. Keep configuration loopable: product identity, datasets, keys, version timestamps, stable base URLs,
  and optional URL templates only when request path or query values vary between calls. Keep request values,
  authentication, pagination, reader settings, extraction windows, and source-specific behavior in notebook code.
- Preserve the documented toolbelt CDC workflow. Do not add abstractions, config extensions, or helper layers unless
  the source requirements and existing toolbelt pattern require them.
- When changing an operational rule, update its owning agent or skill, template or script, and focused test together.
- Never include generated customer projects, temporary state, credentials, or unrelated workspace changes in a commit.
- Keep scripts and tests structural. Validate syntax, shape, types, required keys, naming, and uniqueness — things
  decidable from the file alone and traceable to a written contract. Do not encode meaning or intent: whether a
  value is "operational", redundant, or well-chosen depends on the source system, so a regex over names or values
  produces false positives that block legitimate builds. A false positive is worse than a missing check here,
  because the agent will work around a wrong error rather than surface it.
- Express judgment rules as guidance in the owning agent or skill, ideally as a worked good/bad example. If code
  should still hint, emit a non-blocking `WARN`, never an error. Do not generalize a rule from a single bad output.
- Assert behavior in tests, not prompt wording. Matching exact prose from an agent or skill file makes every
  rewording a test failure and freezes phrasing that should keep improving.

## Validation And Release

- Run the narrowest relevant test after an edit, then run `python3 -m unittest discover -s tests` before publishing.
- Validate edited JSON with `python3 -m json.tool <file>`. Toolpack scripts are standard-library Python so they run
  unchanged on Linux, WSL and native Windows; do not add Bash or PowerShell scripts.
- Before a push, bump `.claude-plugin/plugin.json` and mirror that version in the `marketplace.json` plugin entry.
- Commit only the files needed for the improvement and push only when the user requests publication.
